Scheduler and problem dashboard

How background work is shown and controlled, and where things that need attention show up.

What is agreed

Accepted decisions in the logs.

Central scheduler

  • A central scheduler runs recurring tasks across workflows, such as searches for missing tracks and quality upgrades.
  • Users can see planned and running tasks, their previous results and next scheduled run, and can trigger a task manually in addition to its schedule.
  • Scheduling and task behavior are configurable without the UI, consistent with file-based configuration.

Source logs: 2026-10-17-20-35-00-central-task-scheduling.md, 2026-10-17-20-11-00-file-based-configuration.md

Central problem dashboard

  • A dedicated dashboard gathers exceptional cases across subsystems: uncertain recordings, repeated conflicts with manual identification, download/import problems, and failed or stuck tasks.
  • Entries should make the affected music or task, reason, severity and available follow-up actions understandable, and let users address problems or start reprocessing where applicable.
  • It is distinct from the scheduler overview, which shows normal task activity; the dashboard focuses on exceptions.

Source logs: 2026-10-17-21-25-00-central-problem-dashboard.md, 2026-10-17-21-20-00-manual-identity-authority-and-conflict-alerts.md

Autonomous recovery and history

  • MusicHub tries to resolve recoverable problems itself, such as transient download or task failures.
  • Problems may be visible while recovery is in progress rather than hidden until retries run out.
  • The dashboard distinguishes problems being recovered, those needing user action, resolved ones and recurring ones, and keeps history so resolved and recurring issues stay inspectable.
  • It supports filtering by dimensions such as status, problem type, affected music, task, time and severity.
  • Autonomous recovery must not override manual identity confirmations or other user-controlled decisions.

Source log: 2026-10-17-21-30-00-autonomous-recovery-and-filterable-problem-history.md

Conceptual user journey

An illustrative sequence built from the decisions above; it names no screens, buttons or settings.

  1. Recurring work, such as searching for missing music or upgrades, is listed in the scheduler with last results and next run; the user can trigger a task by hand.
  2. When something goes wrong, an entry appears on the problem dashboard, even while MusicHub is still retrying.
  3. Entries still being recovered need nothing from the user; entries needing action offer follow-ups or reprocessing.
  4. Later, the user filters the history to investigate resolved or recurring problems.

What is not yet decided

  • Task definitions, concurrency, retry policies, cancellation, logs, history retention, permissions, schedule expression format and deployment topology.
  • Severity and status taxonomies, sorting, grouping, filters, saved views and notification rules.
  • Resolution workflows, assignment, suppression, audit history and retention.
  • Retry schedules, limits and escalation; which problems are safe to auto-resolve and which need approval.
  • UI layout and navigation for both the scheduler and the dashboard.
