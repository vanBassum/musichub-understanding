Library and importing

Where MusicHub keeps music, how music gets in, and who owns the library.

What is agreed

Accepted decisions in the logs.

The managed library

  • MusicHub manages its own music library in a user-selected destination folder.
  • MusicHub must not access or scan the user's original NAS music collection; that collection stays out of scope.
  • Music enters through a separate import location or a UI-based import flow, and is ultimately stored in the designated library folder.

Source log: 2026-10-17-20-00-00-managed-library-boundary.md

MusicHub is the authority (version 1)

  • External devices and services may read or copy library files.
  • Changes on a phone or another synchronized copy must not automatically modify, add to, or delete files in the authoritative library.
  • Two-way synchronization is not part of version 1 (provisional scope).

Source log: 2026-10-17-20-05-00-library-authoritative-v1.md

One canonical copy, many groupings

  • One canonical stored copy is kept per genuinely identical track performance/version; distinct mixes and remixes must not overwrite each other.
  • Physical storage is independent of artist, album, compilation and playlist membership. Albums, compilations and playlists are logical references and do not duplicate audio.
  • Internal file storage uses content hashes rather than artist and title as physical paths; identical file content can be deduplicated by hash.
  • Equal hashes are not the same as musical identity: the same recording in different encodings can hash differently, so musical duplicate detection stays with the identification pipeline.

Source logs: 2026-10-17-20-10-00-track-storage-and-export.md, 2026-10-17-20-25-00-unidentified-files-and-content-addressed-storage.md

Exports for other devices

  • MusicHub can generate a separate export with readable artist/title naming and suitable metadata for devices such as phones.
  • Extra storage used by an export is acceptable.

Source log: 2026-10-17-20-10-00-track-storage-and-export.md

Configuration without the UI

  • MusicHub must be fully configurable without its UI, through deployment-managed files and/or environment variables suitable for Docker Compose.
  • A future UI must not become a second, conflicting source of configuration truth.

Source log: 2026-10-17-20-11-00-file-based-configuration.md

Conceptual user journey

An illustrative sequence built from the decisions above; it names no screens, buttons or settings.

  1. The user chooses a destination folder for MusicHub's own library; the existing NAS collection is never scanned.
  2. The user supplies files for import by copying them into an import location or by using a UI-based import flow.
  3. Each file is identified (see Identification and review). Accepted tracks are stored once, under a content-hash-based identity, in the library.
  4. Albums, compilations and playlists reference those canonical tracks.
  5. Optionally, an export with readable names and metadata is produced for a phone or other device; changes made on that copy do not flow back.

What is not yet decided

  • Import staging folder configuration and lifecycle; UI upload mechanisms, format validation, duplicate handling.
  • Exact identity matching and deduplication algorithm; canonical file layout, names or identifiers; hash algorithm and whether it covers whole files or normalized audio.
  • Filesystem versus S3-compatible storage such as MinIO.
  • Export folder structure, synchronization mechanism (including Google Drive integration), playlist file format, presets and artwork selection.
  • Whether future two-way sync is desirable; whether out-of-band edits to the managed folder are detected or repaired.
  • Configuration layout, precedence, validation, secret management, and whether the UI shows read-only or editable settings.
