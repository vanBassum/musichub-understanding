Identification and review

How MusicHub decides what a file is, and what happens when it is unsure.

What is agreed

Accepted decisions in the logs.

Metadata is evidence, not truth

  • Incoming tags are untrusted evidence. Existing artist and title may be used as search hints but do not establish identity.
  • MusicHub aims to identify the exact recording or version in each file, and prefers the original single release when it genuinely contains that recording, otherwise the appropriate original album release.
  • A different recording, mix, remaster or version is never substituted merely to fit the preferred release type.
  • Recording identity and release relationships are kept in the catalog independently of embedded tags, so exports can present different release metadata and artwork.

Source log: 2026-10-17-20-15-00-import-identification-and-release-metadata.md

A configurable, confidence-based pipeline

  • Identification is an ordered, configurable workflow of evidence steps that the user can compose; steps contribute evidence toward a confidence assessment of candidate identities.
  • Costly steps can be skipped once confidence is sufficiently high.
  • High confidence: imported automatically. Intermediate confidence: imported, with the uncertainty recorded and visible for later review and correction. Very low confidence: not imported as an identified library track.
  • A durable review/history view lists identifications that have been uncertain, even if already imported.
  • Outcomes retain provenance: the chosen candidate, supporting evidence, checks performed, confidence and later user corrections.

Source log: 2026-10-17-20-20-00-configurable-identification-pipeline.md

Files that cannot be identified

  • They are not imported into the managed library and remain available for later identification, in the import area or a dedicated quarantine area (placement undecided).

Source log: 2026-10-17-20-25-00-unidentified-files-and-content-addressed-storage.md

Existing versus incoming audio

  • The identification confidence of both the existing recording and the incoming candidate is compared.
  • A confidently identified existing recording is not displaced by a less certain candidate merely because of better encoding quality.
  • Identity confidence and audio quality are separate dimensions and are not collapsed into one score.
  • Uncertain candidates may be retained outside the canonical library and shown in a later review overview.

Source log: 2026-10-17-21-15-00-compare-identification-confidence-of-candidates.md

Manual confirmation wins

  • A user's explicit manual identity confirmation is treated as 100% certain and takes precedence over automated identification, which must not silently overwrite it.
  • If later automated results repeatedly contradict it, MusicHub surfaces a visible alert for review. The alert does not change the identity; only a user correction can.
  • Manual confirmation provenance is kept separate from machine-generated confidence.

Source log: 2026-10-17-21-20-00-manual-identity-authority-and-conflict-alerts.md

Conceptual user journey

An illustrative sequence built from the decisions above; it names no screens, buttons or settings.

  1. A file arrives and its tags are treated as hints only.
  2. The configured pipeline gathers evidence and arrives at a confidence for each candidate identity, skipping costly steps where confidence is already high.
  3. High confidence: the track is imported. Intermediate: imported with uncertainty flagged in the review history. Very low: the file stays out of the library for later identification.
  4. The user can review uncertain items and manually confirm an identity, which then outranks automated results.
  5. If automation keeps disagreeing with a manual confirmation, an alert is raised (see Scheduler and problem dashboard) but the confirmed identity stays.

What is not yet decided

  • Audio fingerprinting, external catalog sources, confidence computation and calibration (including correlated evidence), and numeric thresholds. The 80% figure in the logs was only illustrative.
  • Treatment of remasters versus otherwise identical recordings.
  • Workflow editing UX, allowed step types and short-circuit conditions; whether fingerprints are generated on demand or cached.
  • Review queue UI, timing and workflow; retry and reprocessing controls; how uncertain candidates are stored, approved, rejected or cleaned up.
  • Exact comparison rules, including automatic replacement when both are uncertain; canonical choice when two files represent the same recording.
  • What counts as repeated conflicting evidence, where alerts appear, dismissal and recurrence, and whether a manual confirmation covers one file, one recording or equivalent encodings.
